# Oyster Knowledge Base — architecture, definitions & operations

Oyster's cybersecurity knowledge base is a local, source-attributed, hybrid-retrieval
store. This document defines exactly what is counted, how it is built, and how to audit,
reproduce and extend it. The authoritative, machine-checked numbers live in
[`KNOWLEDGE_100K_EVIDENCE.md`](KNOWLEDGE_100K_EVIDENCE.md) and are regenerated by the
audit script below — never hand-edited.

> **Approved public wording:** _"Oyster indexes more than 100,000 source-attributed
> cybersecurity knowledge chunks."_ Emitted by `GET /knowledge/metrics/public` **only**
> when the live store actually satisfies the threshold; otherwise the sentence is `null`.

## What a "knowledge chunk" is

A row in `knowledge_chunks` (SQLite, in `data/memory.db`) with a matching embedding in the
Chroma index (`data/vector_db`). It counts toward the **eligible unique searchable** total
only when it is ALL of:

1. **Meaningful** — trimmed content length ≥ 40 characters (excludes chunker split-artifacts
   like `)`, `html`, `he program.`, and empty rows).
2. **Stored** — a real row in `knowledge_chunks`.
3. **Searchable** — its `id` is present as an embedding in the Chroma collection its pack
   routes to (`oyster_knowledge`, or `oyster_vulnerabilities` for CVE/CWE/CAPEC), so it is
   retrievable through the normal hybrid RAG path.
4. **Attributed** — a non-empty `canonical_url`.
5. **Uniquely identified** — the row primary key is a stable, deterministic id.
6. **Content-hashed** — a non-empty `content_hash`.
7. **Deduplicated** — counted once per distinct `content_hash`.

## What does NOT count

- Empty, navigation-only, or sub-40-character fragments.
- Exact duplicates (same `content_hash`) — counted once.
- Rows missing a `canonical_url`.
- Rows with no embedding in Chroma.
- **Structured `vulnerability_records`** (≈378k NVD/OSV/GHSA rows) that are reachable by
  exact-id lookup but are **not embedded** as chunks. Counting these would be artificial
  inflation, so the audit explicitly excludes them.

## Sources (authoritative / primary only)

Detection & adversary emulation (Sigma, Splunk Security Content, Azure Sentinel, Atomic Red
Team, YARA/ReversingLabs, WADComs), MITRE (ATT&CK Enterprise/Mobile/ICS via STIX, CWE, CAPEC,
D3FEND), vulnerability intelligence (NVD CVE + CISA KEV/EPSS enrichment), OWASP
(WSTG, API Security, ASVS, MASTG, Cheat Sheets, Top 10, K8s/CI-CD Top 10), cloud & identity
(AWS IAM/KMS/GuardDuty/CloudTrail/Organizations/Security Hub, Azure security, Microsoft Entra,
Kubernetes/Docker security), monitoring (Suricata, Zeek, osquery, Falco), living-off-the-land
(GTFOBins, LOLBAS), standards & supply chain (NIST SP 800-53/207/61/161, OpenSSF best-practices
& Scorecard, SLSA, Sigstore, SPDX, OCSF) and identity protocols (TLS 1.3, DKIM, DMARC, SPF,
OAuth security BCP & native-apps RFCs). Licence-restricted sources (HackTricks NC, Kali,
PayloadsAllTheThings) are gated out before acquisition. See `services/knowledge/connectors/`.

## Ingestion architecture

`connectors/` acquire → licence-validate → normalise → prompt-injection-scan → materialise an
on-disk pack → `pack_service.install()` chunks + embeds + writes provenance. High-volume feeds
(CVE/CWE/CAPEC) use a row-level upsert sync (`services/knowledge/vulnerabilities/`) into the
dedicated `oyster_vulnerabilities` collection.

- **Chunking** — natural record boundaries for CVE/CWE/CAPEC/ATT&CK; heading-aware sections for
  docs; rule-level for Sigma/YARA; test-level for Atomic Red Team.
- **Deterministic ids** — knowledge: `kp::{pack_id}::{doc}::{i}`; vuln: stable per-record ids.
  Re-ingesting **updates** in place (upsert) instead of multiplying rows.
- **Deduplication** — by `content_hash`; the audit and metrics count one row per hash.
- **Attribution format** — every chunk carries `pack_id`, `pack_version`, `canonical_url`,
  `publisher`, `licence`, `trust_level`. Citations resolve to the exact passage via
  `GET /knowledge/citation/{chunk_id}`.
- **Idempotent / resumable** — import jobs are tracked in `knowledge_import_jobs` /
  `vulnerability_import_jobs`; a failed/interrupted run is re-runnable and only touches the
  records that changed. Permanently-unavailable records are recorded, not retried forever;
  transient failures (e.g. NVD `HTTP 503/429`) are distinguished and safe to retry.

## Retrieval path

`services/knowledge/retrieval.py::retrieve()` fuses **vector** (Chroma, both collections) with
**lexical** (FTS5) via reciprocal-rank fusion, re-weighted by trust + freshness, deduped by
hash, diversified per pack. `security_router.py` adds identifier-exact CVE/CWE/CAPEC lookups.
Only installed **and enabled** packs are searched.

## Operations

```bash
# from oyster/backend with venv active
python -m scripts.audit_knowledge                 # authoritative audit (terminal + JSON); exit 0 = PASS
python -m scripts.audit_knowledge --json-only     # machine-readable only
python -m scripts.rebuild_fts --dry-run           # show lexical-index gap
python -m scripts.rebuild_fts                      # repair FTS (additive, idempotent)
python -m scripts.run_retrieval_eval --top-k 5     # retrieval eval; exit 0 = >=90% top-5
python -m pytest -q tests/test_knowledge_100k_audit.py   # audit/metrics/eval unit tests
```

- **Metrics API:** `GET /knowledge/metrics` (full) and `GET /knowledge/metrics/public`
  (display headline). The UI reads the public metric — the count is never hard-coded.
- **Reproduce the count:** `python -m scripts.audit_knowledge --floor 40 --threshold 100000`.
- **Resume interrupted ingestion:** re-run the connector install / vulnerability sync; jobs are
  checkpointed and upserts are idempotent, so no duplicates are created.
- **Source updates:** connectors expose `update-check` (upstream SHA/checksum drift); a re-install
  upserts changed records and bumps `pack_version`.

## Storage & runtime

`data/memory.db` ≈ 1.2 GB, `data/vector_db` ≈ 942 MB. Audit runs in seconds; the set-based FTS
rebuild in ~2 s; the 118-case retrieval eval (real embeddings) in ~45 s.

## Never commit

`data/` (databases, `vector_db`, `reports`, uploads, artifacts), `knowledge_src/`, `.env`, model
weights, downloaded upstream archives. All are covered by `.gitignore`; only source, tests, docs
and the eval-suite JSON are committed.
