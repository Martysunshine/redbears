# --- torch: CPU build, pinned FIRST on purpose -----------------------------
# torch is not a direct dependency — it arrives transitively via
# sentence-transformers (embeddings) and peft (LoRA). Left to resolve on its
# own, pip takes PyPI's default Linux wheel, which is the CUDA build: the image
# shipped torch 2.13.0+cu130 carrying 2.7GB of `nvidia/` and 691MB of `triton/`
# onto a VPS with NO NVIDIA GPU (torch.cuda.is_available() was False). None of
# it could ever execute.
#
# That is not merely wasted space. The deploy of 2026-08-23 FAILED because of
# it: the build ran the disk to 100% and died extracting
# `triton/backends/nvidia/bin/ptxas` — the CUDA compiler — with "no space left
# on device", and left the :latest tag pointing at a half-extracted image.
#
# Pinned to an EXACT +cpu version rather than an --extra-index-url with a loose
# spec, because with a loose spec pip can still legitimately resolve to PyPI's
# CUDA wheel; `2.13.0+cpu` exists only on the pytorch CPU index, so the choice
# is unambiguous. Cost of that precision: bumping torch is now a deliberate
# edit here, and the version must stay compatible with sentence-transformers
# and peft below.
#
# PLATFORM MARKER (do not remove): the `+cpu` local-version tag is published
# ONLY for Linux/Windows. PyTorch ships macOS as a plain `torch==2.13.0` wheel
# (Mac was never CUDA, so it needs no tag). Without the marker below, `pip
# install -r requirements.txt` on a Mac dies with "No matching distribution
# found for torch==2.13.0+cpu" and aborts the WHOLE file — which breaks the
# documented Oyster dev machine (oyster/CLAUDE.md: Apple M5) and Pritika's
# nightly LoRA box (scripts/daily_run.sh, /Users/pritsss). The Linux deploy
# still gets +cpu (the whole point of the disk-space fix); only macOS falls
# back to the plain build, which is CPU-only there anyway.
--extra-index-url https://download.pytorch.org/whl/cpu
torch==2.13.0+cpu ; sys_platform != "darwin"
torch==2.13.0     ; sys_platform == "darwin"
